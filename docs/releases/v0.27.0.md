# v0.27.0 — Workbench Status Dashboard

## Overview

First of three "bigger scope" versions (v0.27.0–v0.29.0). Every workflow
in this app already computes real, read-only health metrics — WebVoc
mapping coverage, mapping registry status counts, open standards
decisions, imported codelists, authored builder fields — but each number
only ever surfaced inside its own workflow. A reviewer had to open every
workflow individually to get a sense of overall project health. This
version consolidates six of those numbers into one panel on the landing
page.

## What changed

- New module `app/workflows/dashboard.py` with
  `render_workbench_status_dashboard(open_sdr_count)`, called from
  `app/streamlit_app.py`'s `main()` right after the page header, before
  the route/workflow selection cards.
- Six metrics, each sourced from an existing function/loader rather than
  new computation:

  | Metric | Source |
  |---|---|
  | WebVoc coverage | `webvoc_explorer.build_explorer_dataset(...).summary` |
  | Registry accepted | `mapping_registry.registry_summary(...)["catalog_by_status"]["accepted"]` |
  | Open SDRs | the standards backlog list already loaded for the sidebar |
  | Codelists imported | the committed `gdsn_codelists_r3_1_36_summary.json` (214 bytes — not the 4.5MB full registry) |
  | Builder fields authored | `builder_expansion_analysis.authored_property_ids(manifest)` |
  | Hard-mapping reviews (session) | `st.session_state["promotion_summary"]`, if set this session |

- Each loader is wrapped in its own `st.cache_data` function, matching
  the caching pattern every other workflow already uses.

## A subtlety worth documenting

The "Hard-mapping reviews (session)" metric is opportunistic, not
authoritative: it only reflects a value if the reviewer has already run
Generate Mapping Candidates in the current session, and because this
dashboard renders earlier in the script than that workflow, on the exact
run where the reviewer clicks "Generate Candidates" this panel still
shows the *previous* rerun's value — it catches up on the next rerun.
It's deliberately labeled differently from Generate Mapping Candidates'
own "Hard-mapping reviews recorded" metric (which is always current) so
the two aren't confused. A test failure caught this exact ambiguity
during development — the fix was the distinct label, not new logic.

## What did NOT change

- No new data source, no new file writes, no change to any workflow's own
  rendering or computation.
- WebVoc coverage numbers match Explore's own display exactly (both read
  the same summary); the low percentage (~1%) is expected and already
  documented in `docs/webvoc-explorer.md` — `mapped_property_count` is
  intentionally conservative, excluding candidate/experimental/
  schema.org-fallback rows.

## Preserved

- No warnings suppressed; no mock data; no fabricated coverage/compliance.
- No official GS1 validation or production compliance claimed.
