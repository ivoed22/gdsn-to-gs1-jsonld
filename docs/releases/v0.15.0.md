# v0.15.0 — Mapping Profile Consolidation

## Overview

Version v0.15.0 consolidates the mapping foundation ahead of full-scope
mapping scoring (Track B), visual smoke tests, and the GS1-first DPP
Crosswalk. One artifact — `mapping/mapping_registry.yaml` — is now the
current, authoritative mapping profile; the three older profiles are archived
out of the primary user flow but kept on disk for reference and comparison.

**Converter behavior is unchanged and test-proven:** converting the example
XML with the registry produces byte-identical JSON-LD, mapping reports,
validation reports, and unmapped-field reports compared to
`mapping_v0_3.yaml`.

## The consolidated registry

`mapping/mapping_registry.yaml` merges two previously separate artifacts:

- the executable mapping profile (`mapping/mapping_v0_3.yaml`, 28 mapped GDSN
  attributes), copied structurally identical, and
- the governance review catalog
  (`mapping_catalog/gdsn_to_gs1_web_vocabulary_mapping_catalog_v0_3_webvoc_validated.csv`,
  29 review rows), preserved in full.

Structure:

- `fields` / `object_mappings` — the only sections the converter executes;
  identical to v0_3. Each field carries a `governance` block (status,
  original `catalog_status`, confidence, `review_required` flag, source) that
  the converter's loader ignores.
- `catalog` — the complete review catalog as a top-level list the converter
  never reads. Registry statuses use a fixed vocabulary — proposed /
  review_required / accepted / rejected / deprecated / blocked — and the
  original catalog `mapping_status` values are preserved verbatim as
  `catalog_status`, so no review provenance is lost. All 29 current rows are
  implemented in the executable profile (status `accepted`); 17 carry
  `review_required: true` because their catalog status is not yet fully
  reviewed (`candidate_*`, `needs_*_review`).

The artifact is generated deterministically by
`scripts/build_mapping_registry.py`; regenerating yields identical content
(enforced by test). Do not edit it by hand — changing accepted mappings
remains a reviewed standards decision.

`src/gdsn_to_gs1_jsonld/mapping_registry.py` provides the governance view
(per-field governance blocks, catalog rows, summary counts) for review
tooling. Track B (v0.16.0) builds on this.

## Archived profiles (UI)

- The sidebar shows an **"Active mapping profile"** panel with the registry
  and a `Current` status badge by default.
- `mapping_v0_3.yaml`, `mapping_v0_2.yaml`, and `mapping_mvp.yaml` are
  **archived**: kept on disk, listed only inside an "Archived mapping
  profiles" expander, and selectable for reference/comparison. Selecting one
  shows a visible warning ("Archived profile — for reference/comparison
  only…"), an `Archived` badge, and clears current conversion results —
  users no longer need to understand old profile history to start converting.

## Design tokens & status badges

`app/ui.py` gains a reusable status-badge component built on the existing
semantic color tokens: `current` (blue), `accepted` (green), `review`
(amber), `blocked` (red), `archived` (grey). Badges always carry a text
label — never color-only.

## New policy test suites

- `tests/test_mapping_registry.py` — registry loads; executable sections and
  conversion output are identical to v0_3; catalog view and governance
  blocks are complete; the status vocabulary is enforced (no
  `hard_mapping_candidate` status exists); the generation script is
  deterministic.
- `tests/test_no_claims.py` — claim-shaped phrases (official GS1 validation,
  EU DPP compliance, production readiness) appear only in negated form on
  the landing page and the Vocabulary & Mapping and Product Passport Bridge
  routes; the sidebar governance negations must stay present.
- `tests/test_no_dppk.py` — DPP Keystone (dppk) terms and namespaces never
  appear in generated or recommended output (mapping, app, src, examples,
  builder manifest, product passport, scripts, tests). Documentation may
  reference DPP Keystone as external tooling inspiration only.

## CI

- The mapping-candidates smoke now runs against the registry.
- A new `check-mapping` smoke guards registry ↔ catalog consistency (0
  errors; the 12 pre-existing catalog review warnings are unchanged and
  remain visible).

## Preserved

- Converter logic, batch behavior, and single-file output are unchanged
  (byte-identical, test-proven).
- `mapping_catalog/*`, Web Vocabulary snapshots, the builder manifest, and
  all existing mapping YAML files are unchanged.
- No warnings suppressed; no mock data; no fabricated coverage/compliance.
