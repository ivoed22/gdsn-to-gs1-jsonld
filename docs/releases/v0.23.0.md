# v0.23.0 — Full WebVoc Codelist Option in Manual Builder

## Overview

This version was originally planned as "populate real codelist dropdowns
for the Manual Builder's `codelist_pending` fields, using Track D's
`CODELIST_DEPENDENCIES`." Investigation before implementation found that
premise didn't match the current builder manifest — see "What we found"
below — so the plan was corrected to the genuinely verified gap instead.

## What we found

Checking all 6 `CODELIST_DEPENDENCIES` canonical fields against
`builder_manifest/product_builder_v0_10.yaml`:

| Canonical field | Builder reality |
|---|---|
| `net_content_unit` | `gs1:netContent` is an `input_type_override: quantity` sub-field (value + free-text unit code), not a `code`-type field. |
| `allergens[].allergen_type` | `gs1:allergenType` (nested under `gs1:hasAllergen`) already has 14 curated options — but that's a hand-picked EU subset, not the full codelist. |
| `allergens[].level_of_containment` | `gs1:allergenLevelOfContainmentCode` already has all 3 real `LevelOfContainmentCode` values curated. No gap. |
| `nutrients[].nutrient_type_code` / `preparation_state_code` | Both live under `gs1:nutrientDetail`, which is `supported_in_v0_10: false` — not authorable in the builder at all yet. |
| `referenced_documents[].referenced_file_type` | No authorable builder field maps to `ReferencedFileTypeCode`. |

A full scan of every `input_type_override: code` field in the manifest
confirmed every single one already has manifest-curated `options` — zero
fields are currently `codelist_pending`. The original plan's premise (six
pending placeholder fields waiting to be filled) did not hold.

The one concrete, verified, valuable gap: `gs1:allergenType`'s 14 curated
values are a hand-typed EU subset. The local WebVoc snapshot
(`webvoc/current/gs1Voc.jsonld`) itself defines 385 named individuals of
class `gs1:AllergenTypeCode` — the real, full, authoritative set, already
committed and available offline.

## What changed

- New `webvoc_explorer.group_individuals_by_class(data)`: a generic
  function that groups every WebVoc-defined named individual (any
  `@graph` item that is neither a class nor a property) by its `@type`.
  For `gs1:AllergenTypeCode` this returns all 385 defined values with
  `rdfs:label`-derived labels; for `gs1:LevelOfContainmentCode`, all 3.
- `app/workflows/prototype.py`:
  - `_property_metadata_index` now also computes
    `full_codelist_options` per property from its own WebVoc `range`
    class(es) — generic, not hardcoded per field.
  - Object sub-fields (like `gs1:allergenType`, nested under
    `gs1:hasAllergen`) get this fallback merged in too.
  - The `code`-type widget renderer shows a "Show full code list (N
    total) instead of the curated M" checkbox whenever the WebVoc-derived
    full set is strictly larger than the manifest's curated `options`.
    Unchecked (default) is byte-identical to pre-v0.23.0 behavior.
- `builder_status.compute_field_status`: a field is `codelist_pending`
  only if both `metadata["options"]` and the new
  `metadata["full_codelist_options"]` fallback are empty. No currently
  authorable field is affected (all already have curated options), but
  status stays correct if a future manifest field ships with no options.

## Why this is the generic, not one-off, right shape

The mechanism keys off each property's own declared WebVoc `range`, not a
hardcoded per-field table. Any current or future builder `code` field
whose manifest options are a subset of what WebVoc actually defines gets
the same "show full list" affordance automatically — no per-field wiring
needed. `gs1:allergenLevelOfContainmentCode` correctly gets **no**
checkbox, because its curated 3 already equal WebVoc's full 3.

## What did NOT change

- Default behavior for every field: unchanged (curated options remain
  the default view; nothing is silently expanded).
- No manifest YAML edits — the curated subsets stay as documented,
  intentional defaults; the full list is opt-in via the checkbox.
- No fabricated values: every option in the "full" list is a real,
  locally-committed WebVoc-defined individual, never invented.
- `net_content_unit`, `nutrient_type_code`, `preparation_state_code`, and
  `referenced_file_type` remain out of scope for this version — they
  aren't currently modeled as authorable `code`-type builder fields, and
  making them so is a larger, separately-scoped change.

## Preserved

- No warnings suppressed; no mock data; no fabricated coverage/compliance.
- No official GS1 validation or production compliance claimed.
