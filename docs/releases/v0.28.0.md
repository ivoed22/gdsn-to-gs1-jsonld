# v0.28.0 — Load a Previously Generated Candidate Report

## Overview

This version was originally planned as "a viewer for the CLI's
`--full-scope` sweep output, since that's too slow to run live inside
Streamlit." Investigation before implementation found that premise
didn't match the code — see "What we found" below — so the plan was
corrected to the genuinely useful capability instead.

## What we found

`gdsn-to-gs1-jsonld generate-mapping-candidates --full-scope` and the
Streamlit Candidates workflow's "All properties" option call the exact
same function: `mapping_candidate_generator.generate_all_candidates`.
There is no separate, more-expensive "full scope" code path — `--full-
scope` is just the CLI's name for "no `--property` filter," identical to
selecting "All properties" in the dropdown. The Streamlit UI already
supports running this (with a cautionary caption pointing to the CLI),
so there was nothing distinct to build a "full-scope viewer" for.

What's real: this scan is genuinely expensive (~7 minutes, all 553 WebVoc
properties against ~6,067 GDSN attributes) regardless of which entry
point triggers it, and Streamlit has no session persistence across app
restarts — so a reviewer who already ran this once (via CLI or UI) has
no way to look at that result again without re-running the whole scan.
**That's** the real gap, and it doesn't require fabricating a "full-scope
concept" that doesn't structurally exist.

## What changed

- New `app.workflows.candidates.parse_uploaded_candidate_report(raw_bytes)`
  — pure validation, no Streamlit API calls. Accepts the exact JSON shape
  `candidate_report_bytes_json`/`write_candidate_reports` already produce
  (a flat array of candidate dicts). Requires each entry to have at least
  `candidate_id` and `webvoc_property_id`; silently drops anything else
  is wrong, raises `ValueError` with a specific message if the whole file
  or every entry is unusable.
- Generate Mapping Candidates gains, in the Controls section:
  - A caption explaining the CLI's `--full-scope` option and pointing out
    it's the same cost as the UI's "All properties."
  - A file uploader ("Load a previously generated candidate report
    (JSON)") and a "Load report" button.
  - On load: the parsed candidates are run through
    `mapping_promotion.build_promotion_artifact` (using whatever
    hard-mapping review sign-off file is currently uploaded), then stored
    in the same session-state keys the live-generation path uses.
- New `_store_candidate_results(candidates, reviewed_hard_mapping_ids)`
  helper factors the annotate-and-persist step out of the live
  "Generate Candidates" button handler, now shared by both paths — no
  duplicated logic, and the existing metrics/table/detail/sign-off/
  download UI renders identically regardless of which path populated it.

## What did NOT change

- `generate_all_candidates`, `generate_candidates_for_property`, and the
  CLI's `--full-scope` flag are untouched.
- No new scoring, no re-computation of candidate data — loading a report
  only re-runs the (cheap, deterministic) promotion-annotation step, not
  the (expensive) GDSN-attribute matching/scoring step.
- The existing "All properties" live-generation path in the UI is
  unchanged and still available for smaller ad-hoc runs.

## Preserved

- No warnings suppressed; no mock data; no fabricated coverage/compliance.
- No official GS1 validation or production compliance claimed.
